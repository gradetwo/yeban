Troubleshooting

人谁无过？过而能改，善莫大焉。

Zuo Zhuan, 2nd year of Duke Xuan (《左传·宣公二年》)

Translation: “Who among us has no faults? To err and be able to change is the greatest good.” Mistakes are not the end: follow the clues, correct the cause, and the project moves on.

This chapter is organised by symptom: what you see, then what to rule out. Each section moves from the most likely and easiest-to-check cause towards project and device levels; change one thing at a time and audition after each. One guiding rule throughout: Yeban records key facts in receipts and the status bar — do not conclude from "it looks fine".

No Sound

Work through these in order, changing only one thing per step and listening after each:

  1. Transport and playhead: is playback actually running? Press Space and watch the playhead advance; Shift+Space resumes from the cursor.
  2. Mute / solo: are Mute or Solo engaged on the track header or in the mixer? If another track is soloed, the current one is silent by design.
  3. Fader and pan: is the track fader or master fader all the way down? Mix $$ Reset Master Fader to 0dB restores the master in one step.
  4. Device chain: did the instrument load? Is an effect bypassed? Bypassed devices are not the same as deleted ones.
  5. Clip and fades: is there actually a clip under the playhead? Was it trimmed down to silence, or are its fade-in/fade-out swallowing the whole thing?
  6. Materials present?: a missing embedded sample is recorded as MissingSample and the track is skipped (saving still succeeds). Check the asset pool for the audio it uses; relative SFZ paths depend on the project directory — a project opened from file uses the real directory, while an unsaved new project uses a placeholder under the output directory, which breaks samples kept only next to the project file.
  7. Control Room: does the master-bus meter show a level? Level present but nothing heard points to the output device; no level points to the project side.

Devices and Drivers

Input device and level

The recording panel has input-device selection and an input test, so you can confirm a signal arrives before actually recording. The recording path uses the project's sample rate (48 kHz by default); after changing devices, the next recording uses the new one.

Output and latency

If the project-side meter shows level but you hear nothing, check the system output device and the Control Room's master-bus reading. Yeban targets low-latency determinism and handles internal plug-in delay compensation; for latency-sensitive work, check the device buffer settings first rather than hunting for interface switches.

Safe defaults

Network-listening services (MCP HTTP) bind only the loopback address 127.0.0.1, never 0.0.0.0; a default build does not listen at all unless you explicitly pass --enable-mcp-http or set YEBAN\_MCP\_HTTP=1. If MCP "won't connect" and you are tempted to open up listening, check that runtime switch first — do not change the bind address.

A Project Will Not Open

  1. Check the file: .yeban is the only project format. Saving is atomic, so a power cut mid-write usually leaves the previous complete version rather than half a file; try a backup if you have one.
  2. Use the right entry: File $$ Open / Restore Project..., or yeban-app --open ; the startup chooser's Recent Projects tab also returns you to prior work.
  3. Are the assets alongside it?: the project references asset-pool materials by content hash. If you copied only the .yeban file and lost referenced materials, the project opens but those tracks are silent — that is not "won't open".
  4. Export a diagnostic bundle: Diagnostics $$ Export Project Diagnostic Bundle produces a troubleshooting bundle (not artwork audio). Attaching it is far more useful than a vague description when asking for help.
  5. Record errors verbatim: if the app reports an error code or a missing list, note the original text; do not substitute "it looks like the same problem as last time" for a measurement.

Performance and Memory Thresholds

Know the threshold

The app test target is heavy: measured on a 4 GB machine, cargo test -p yeban-app is killed by the kernel (rustc SIGKILL) at roughly 35 minutes, yielding no results; moving the same kind of assertions into a lighter crate (yeban-model) compiled in about 1m39s and ran in about 1s. The practical threshold for app-side verification is at least 8 GB; below it, app-side work can only be static changes — do not claim tests were run.

A minimum verification set when resources are tight

When memory is insufficient, use the smallest set you can actually complete: cargo fmt --check, cargo check --all-targets and clippy for the target crate. Record what could not run honestly as not\_run with the reason, and let CI rerun it on a larger machine. For building, use cargo build --profile release-small -p yeban-app; on a headless machine add --headless.

Only the CI verdict counts

A local green is only a reference; the final verdict belongs to CI. An unread verdict counts as pending, never as "passed". Also avoid treating an overall "success" as proof that the target assertions actually ran — confirm the job executed (non-zero duration) and its log contains test-result lines.
