# 编排配器 Skill（音源选型与 SFZ 制作）

核心方法论：**选库先审计（数据说话），入库先清洗（CC 门/轮替/键位逐项核对），接引擎先小样验证（单轨最小工程试触发）**。

## 1. 选库流程

1. **先定音色画像**：从参考曲提取目标频谱重心（Hz）与音区，再去找库，而不是先找库再硬凑
2. **候选库逐个审计**，用数据筛掉"名字对但声音错"的：
   - 频谱重心：失真吉他 ~1.5–2 kHz、清音/木吉他 ~300–800 Hz、贝斯 ~150 Hz 量级；重心明显偏离画像的库直接淘汰
   - 听 1–2 个采样原始波形，确认没自带效果（自带失真/混响/压缩的库后期救不回来）
   - 确认乐器类型（尼龙弦古典吉他 ≠ 电吉他清音，听一个音就能分辨，别只看库名）
3. **来源渠道**：GitHub（freepats、karoryfer、sfzinstruments 等 org）为主；下载慢时用 ghfast.top 类镜像加速

## 2. SFZ 制作与清洗（硬规则）

**逐项核对清单，每项都是真实踩过的坑：**

- [ ] **随机轮替**：优先 `lorand/hirand`（SFZ v1 起支持）；若目标引擎不识别，改写为 `seq_length/seq_position`。层叠不轮替 = 多层叠加炸响，一耳朵就能听出来
- [ ] **CC 初始状态**：`<control>` 段的 `set_ccN` 是**初始状态播种**，不是运行时事件；库若用 `loccN/hiccN` 门 + `set_ccN` 组合，离线渲染必须把 CC 门静态化（按 set_ccN 折算成 region 条件或预置 CC 值），否则整库静音
- [ ] **一行多键**：`locc25=32 hicc25=47` 这类多 opcode 行要按 opcode 正则逐对解析，`split('=')` 只取第一对会静默丢键位
- [ ] **`<master>` 头部参数**：`<master> key=$xxx` 的参数必须下传到子 region，丢掉 = 整组键位缺失
- [ ] **keytrack**：默认 `pitch_keytrack=100`（每键 100 音分）。单行 `key=0-127` 写法部分引擎不识别，分行写 `key=0` … `key=127` 最稳
- [ ] **offset_random / sw_default** 等变体 opcode 逐个验证引擎支持情况，不支持就静态化
- [ ] 清洗后的库跑**单音触发测试**（每个目标键位出声才算过），再跑全曲

## 3. 引擎兼容性验证（接新库必做）

最小验证三步，10 分钟换回半天排障：

1. 单 region 单音 SFZ → 引擎触发，确认出声
2. 全键位扫描（42/44/46 这类"边缘键位"最容易缺）
3. CC 门场景：CC=0 与 CC=100 两臂对比，确认门逻辑生效

**已知问题模式**（遇到静音/无声按此排查顺序）：
- CC 门未播种（离线渲染路径没吃到 CC 初始状态）
- `lorand` 被当普通 region 全部叠加
- `<master>` 参数丢失导致键位映射缺失
- 采样率/格式不被解码（先试 wav 16bit/44.1k）

## 4. 配器搭配原则

- **同一首歌里每个频段只留一个主角**：低频贝斯+kick 二选一撑底；中频人声为主、吉他让位；高频军鼓/镲点缀
- 双吉他/多轨吉他：音区错开（节奏低把位 + 华彩高把位），同把位叠两轨只会糊
- 鼓组选型看三点：kick 有无 40–60 Hz 下潜、军鼓音色性格（胖/薄）、闭镲密度；不要用"全采样都很大"的库
- 力度层次靠 velocity 分层采样（vel layers ≥3 层）的库表现最好，单层库力度是假的

## 5. 验收清单

- [ ] 每轨目标键位全部触发出声（全键位扫描）
- [ ] 轮替生效（同一音符连打 N 次，波形不同/能量不叠）
- [ ] 频谱重心落在音色画像 ±20%
- [ ] 多层无叠加炸响（对比单 region 与完整库同音符峰值差 <3 dB）
- [ ] 离线渲染与实时预听结果一致（若引擎有两条渲染路径，必须都验证）

## 6. 反模式

- ❌ 按库描述/图标选音色，不审计实际频谱
- ❌ 直接拿原始库进工程，不做 CC/轮替清洗
- ❌ 只测一个音就全曲渲染
- ❌ 音色问题试图用 EQ 硬调（自带失真的库砍不回清音）
- ❌ 假设引擎支持全部 SFZ opcode
