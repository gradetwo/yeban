# 夜半 UI · 错误与提醒的设计原则

> 适用范围：**所有**面向用户的报错、警告、提醒、状态行（引擎、音源、导出、设备、工程加载…）。
> 这份文档是评审依据：新增一条提示时，逐条对照。

## 0. 一句话

**报错本身不产生价值；让用户点一下就把问题解决掉，才产生价值。**

用户不是工程师。`SFZ 摊平失败: 读 SFZ 失败: SFZ 路径 …` 这种串，对他等于"什么都没说"。
他看到的是：工程打开了、按播放没声音、界面一切正常 —— 于是他关掉重开、重装、或者干脆放弃。

## 1. 必须给出「下一步动作」

每条面向用户的错误/警告，至少要有**一个可以直接点的动作**，且动作要能真的解决问题：

| 场景 | ❌ 只报错 | ✅ 可点一下解决 |
| :--- | :--- | :--- |
| 工程里的音源没装，且在内置清单里 | "SFZ 路径找不到" | 自动打开音源管理、按这件音源筛好 ⇒「下载」 |
| 音源不在清单里 | "读 SFZ 失败" | 说明"清单里没有这件"，并让用户按类别挑一件同类音源换上 |
| 音频设备打开失败 | "音频设备未接线" | 提示"本会话无声"，并给出可选的设备/降级说明 |
| 导出失败 | 一行技术原因 | 说明失败在哪一步 + 保留原文件 + 给出重试/换格式 |
| 下载失败 | HTTP 错误码 | 写明"网络中断/文件校验不符"，并给「重试」 |

没有动作的错误只有两类可以接受：
1. 用户**完全无法**介入的（例如"本机不支持该采样率"）—— 那要给出**替代方案**；
2. 一次性提示（例如"[卷帘] 已清除选中态"）—— 那是**状态反馈**，不是错误。

## 2. 主文案用人话，术语降到「详情」层

* **标题 / 主文案**：说"发生了什么、影响是什么"，用用户的语言。
  * ✅「这个工程有 2 条轨的音源没装」
  * ❌「引擎快照投影失败」
* **技术原文**（错误链、路径、错误码）：保留，但放在第二行或「详情」里，供上报与排查。
  * 原则：**可以看不懂，但不能看不到**（见第 4 条）。
* 术语只在两种情况下出现在主文案：用户自己就是这么说的（"SFZ 文件"），或该术语就是他的操作对象（"音源管理"）。

## 3. 一键 = 真的只需一次点击

* 「引导到音源管理」不是让用户自己找菜单：**直接替他打开**，并把缺失件**筛到列表最前**。
* 列表里的按钮文案就是动作本身（「下载」「装到这条轨」），不是「确定」。
* 需要多步的（先下载再指定给轨道），要么自动串起来，要么在状态行写清"还差哪一步"。
* 任何"请检查网络后重试"都必须同时给出「重试」按钮。

## 4. 不许静默：终端看得见的，界面必须看得见

* 任何 `eprintln!` / CLI 输出的**失败**，都必须在 UI 里有对应呈现（横幅 / 状态行 / toast）。
* 唯一的写入口径：同一类状态只由**一个**宿主函数写进界面属性（例如引擎错误只由
  `host::apply_engine_error` 写 `engine-error`），避免"两处各写一份、互相对不上"。
* 反向也成立：界面属性是**原文**，不是压扁的 bool —— 用户与判据都要能读到具体原因。

## 5. 提示的分级与落点

| 级别 | 含义 | 落点 | 是否可关闭 |
| :--- | :--- | :--- | :--- |
| 状态反馈 | "已经做了什么" | 状态栏 / toast | 自动消失 |
| 提醒 | "你可能想知道"（无声卡、降级） | toast + 状态行 | 可关闭 |
| 警告 | "能继续，但有损失"（资产缺失） | 横幅（不遮挡编辑区） | 可关闭，解决后自动消失 |
| 错误 | "做不成了" | 横幅 / 对话框 | **保留到问题解决**，⛔ 不许一闪而过 |

* 错误横幅**不许自动消失**：心跳每秒 60 次，"这一跳没发生什么"不等于"问题好了"。
* 关闭错误横幅 ≠ 问题已解决：再次发生时必须**重新出现**。

## 6. 可访问性与可判性

* 每一个可点的提示元素都要有 `accessible-id`（`[UI-TEST-001] §12.2`）—— 否则判据点不到，
  用户用读屏也找不到。
* 文案走 `@tr`；技术原文（路径、错误码）不走——它不是界面文案。

## 7. 失败不留半成品

* 下载/安装/导入失败 ⇒ 临时文件清理干净，已安装区**一位不动**。
* 校验失败 ⇒ 删掉刚装的那份（而不是留一个"看起来装好了"的目录）。
* 状态行必须写清"回滚了没有"。

## 8. 总结成一张检查表

新增任何提示前问四句：

1. 用户看得懂这句吗？（不懂 ⇒ 换成影响描述）
2. 他知道下一步点哪吗？（不知道 ⇒ 加动作）
3. 这个动作一次点击够吗？（不够 ⇒ 自动串起来）
4. 界面看得见吗？（只有终端有 ⇒ 补 UI）
