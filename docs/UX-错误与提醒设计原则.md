# 夜半 UI · 错误与提醒的设计原则

> 适用范围：**所有**面向用户的报错、警告、提醒、状态行（引擎、音源、导出、设备、工程加载…）。
> 这份文档是评审依据：新增一条提示时，逐条对照。

## 0. 一句话

**报错本身不产生价值；让用户点一下就把问题解决掉，才产生价值。**

用户不是工程师。`SFZ 摊平失败: 读 SFZ 失败: SFZ 路径 …` 这种串，对他等于"什么都没说"。
他看到的是：工程打开了、按播放没声音、界面一切正常 —— 于是他关掉重开、重装、或者干脆放弃。

## 1. 必须给出「下一步动作」

每条面向用户的错误/警告，至少要有**一个可以直接点的动作**，且动作要能真的解决问题：

| 场景 | ❌ 只报错 | ✅ 可点一下解决 |
| :--- | :--- | :--- |
| 工程里的音源没装，且在内置清单里 | "SFZ 路径找不到" | 自动打开音源管理、按这件音源筛好 ⇒「下载」 |
| 音源不在清单里 | "读 SFZ 失败" | 说明"清单里没有这件"，并让用户按类别挑一件同类音源换上 |
| 音频设备打开失败 | "音频设备未接线" | 提示"本会话无声"，并给出可选的设备/降级说明 |
| 导出失败 | 一行技术原因 | 说明失败在哪一步 + 保留原文件 + 给出重试/换格式 |
| 下载失败 | HTTP 错误码 | 写明"网络中断/文件校验不符"，并给「重试」 |

没有动作的错误只有两类可以接受：
1. 用户**完全无法**介入的（例如"本机不支持该采样率"）—— 那要给出**替代方案**；
2. 一次性提示（例如"[卷帘] 已清除选中态"）—— 那是**状态反馈**，不是错误。

## 2. 主文案用人话，术语降到「详情」层

* **标题 / 主文案**：说"发生了什么、影响是什么"，用用户的语言。
  * ✅「这个工程有 2 条轨的音源没装」
  * ❌「引擎快照投影失败」
* **技术原文**（错误链、路径、错误码）：保留，但放在第二行或「详情」里，供上报与排查。
  * 原则：**可以看不懂，但不能看不到**（见第 4 条）。
* 术语只在两种情况下出现在主文案：用户自己就是这么说的（"SFZ 文件"），或该术语就是他的操作对象（"音源管理"）。

## 3. 一键 = 真的只需一次点击

* 「引导到音源管理」不是让用户自己找菜单：**直接替他打开**，并把缺失件**筛到列表最前**。
* 列表里的按钮文案就是动作本身（「下载」「装到这条轨」），不是「确定」。
* 需要多步的（先下载再指定给轨道），要么自动串起来，要么在状态行写清"还差哪一步"。
* 任何"请检查网络后重试"都必须同时给出「重试」按钮。

## 4. 不许静默：终端看得见的，界面必须看得见

* 任何 `eprintln!` / CLI 输出的**失败**，都必须在 UI 里有对应呈现（横幅 / 状态行 / toast）。
* 唯一的写入口径：同一类状态只由**一个**宿主函数写进界面属性（例如引擎错误只由
  `host::apply_engine_error` 写 `engine-error`），避免"两处各写一份、互相对不上"。
* 反向也成立：界面属性是**原文**，不是压扁的 bool —— 用户与判据都要能读到具体原因。

### 4.1 三个落点各自的职责（2026-11-19 审计后定型）

审计的结论是：本仓当时**只有 2 条提示通道真的活着**（toast / engine-error）。其余
"模块回执"30 处写入属性却 0 处渲染、58 处用户手势失败只写 stderr ⇒ 用户看到的是
"点了没反应"。现在固定成三个落点，谁写谁读都登记在这里：

| 落点 | 宿主写入函数 | 界面容器 | 用在什么场合 |
| :--- | :--- | :--- | :--- |
| **回执行** | `report_notice` / `apply_module_receipt*` / `report_rejected` | `app.slint` 布局内 `module-receipt-line`（空读数时不占高度） | 一切"刚刚这一步做成了/没做成"的动作回执。**保底通道**：布局溢出时它仍在窗口里 |
| **提示条** | `report_notice`（`toast-is-error` 分级） | `app.slint` 的 `toast-banner` | 短句确认与失败提醒；信息级 4 秒自动收走，错误级常驻 |
| **横幅** | `apply_engine_error` | `app.slint` 的 `engine-error-banner` | 引擎级问题（缺音源、快照投影失败）。横幅里**必须**带一个"下一步按钮" |

三条硬规则：

* **同一件事只写一个落点函数**（⛔ 不各写一份），落点函数内部同时写回执行与提示条；
* 回执行读的是 `module-status-text`（人话），`module-status` 保留结构化原文给判据；
* 回执行的 ✕ 只是"收起来"，下一次动作会再写回来 —— 它**不是**"已解决"。

## 5. 提示的分级与落点

| 级别 | 含义 | 落点 | 是否可关闭 |
| :--- | :--- | :--- | :--- |
| 状态反馈 | "已经做了什么" | 状态栏 / toast | 自动消失 |
| 提醒 | "你可能想知道"（无声卡、降级） | toast + 状态行 | 可关闭 |
| 警告 | "能继续，但有损失"（资产缺失） | 横幅（不遮挡编辑区） | 可关闭，解决后自动消失 |
| 错误 | "做不成了" | 横幅 / 对话框 | **保留到问题解决**，⛔ 不许一闪而过 |

* 错误横幅**不许自动消失**：心跳每秒 60 次，"这一跳没发生什么"不等于"问题好了"。
* 关闭错误横幅 ≠ 问题已解决：再次发生时必须**重新出现**。

## 6. 可访问性与可判性

* 每一个可点的提示元素都要有 `accessible-id`（`[UI-TEST-001] §12.2`）—— 否则判据点不到，
  用户用读屏也找不到。
* 文案走 `@tr`；技术原文（路径、错误码）不走——它不是界面文案。

## 7. 失败不留半成品

* 下载/安装/导入失败 ⇒ 临时文件清理干净，已安装区**一位不动**。
* 校验失败 ⇒ 删掉刚装的那份（而不是留一个"看起来装好了"的目录）。
* 状态行必须写清"回滚了没有"。

## 8. 总结成一张检查表

新增任何提示前问四句：

1. 用户看得懂这句吗？（不懂 ⇒ 换成影响描述）
2. 他知道下一步点哪吗？（不知道 ⇒ 加动作）
3. 这个动作一次点击够吗？（不够 ⇒ 自动串起来）
4. 界面看得见吗？（只有终端有 ⇒ 补 UI）
5. 用户**一次点击**能不能真的恢复？（不能 ⇒ 那是"提示"，不是"解决"）

### 8.2 缺音源：把"报错"变成"换成能响的"（2026-11-19）

打开工程发现某条轨的音源没装，旧行为是"丢一句术语 / 直接塞进音源管理自己找"。
现在的口径是**救援面板**：打开工程即弹出，一屏内每条轨一行，行内三件事：

| 情况 | 界面给的 | 用户动作 |
| :--- | :--- | :--- |
| 清单里有这件（可下载） | 「下载原音源」 | 一次点击 ⇒ 音源管理已筛好这一件 |
| 清单里没有，但有同类且本机已装 | 「换成 X」 | 一次点击 ⇒ 立刻提交 `Op::SetTrackSampler`，**当下就能响** |
| 清单里没有，同类也没装 | 「下载 X」 | 一次点击 ⇒ 去下载；**装好那一刻自动换上这条轨** |

三条硬规则：

* **"换成"只列本机已装的**：给一个还没有的音源让他"换"，结果还是静音 —— 那不是解决，
  是第二次失败；
* **同类判定以轨名为第一线索**（`missing_sounds::infer_kind`），路径只作补充；认不出来就
  不假装懂行，按体积从轻到重兜底；
* **候选至多 3 个**：这个面板要一眼扫完，⛔ 不做成第二个音源管理列表；
* **点过「下载」就不用再点第二次**：装好那一跳由宿主接管
  （`host::rescue_after_pack_installed`），自动换到"等着这件音源"的那条轨，并说一句
  "装好了，已自动换上：X（轨名）"。用户点过一次，就不该再为同一件事点第二次 ——
  这是底线，不是优化项。

#### 8.2.1 装好之后还得能"用上"（音源管理的「用到当前轨」）

救援面板只处理"这条轨缺东西"；用户在音源管理里**主动**装了一件音源之后，同样会卡在
"装好了，然后呢？"。所以列表里装好的那一行不再是一枚不可点的"已安装"标签，而是一枚
**「用到当前轨」**：

* 目标是**混音台当前轨**，面板标题右侧直接写"用到当前轨 ⇒ 鼓组"，⛔ 不让人猜是给谁的；
* 点一下 ⇒ 提交 `Op::SetTrackSampler`，状态行如实说"已把「X」用到「轨道名」。回到工程按播放就有声音"；
* 混音台没有可用轨 ⇒ 如实说"先在混音台选一条轨"，⛔ 不猜一条轨替用户决定；
* 包里解析不到 `.sfz` ⇒ 如实说"装得不完整，请在混音台手动指定文件"，⛔ 不写猜出来的路径。


### 8.3 弹层、迁移与"过期警报"（2026-11-19 第二轮，用户截图点破的三条）

用户在音源缺失现场贴了两张图，暴露的不是文案问题，而是**交互链上的三个硬 bug**：

| 现场 | 病根 | 现在的规则 |
| :--- | :--- | :--- |
| 救援面板压在音源管理上面，点「下载」后看不见进度与结果 | 两层弹层的 `z` 值写反（救援 9650 > 音源管理 9600），且打开时不收前者 | **① 一次只当面一个"决策层"**：去下载 = 救援面板先让位（`missing-sounds-open=false`），音源管理在前台；装完/关掉后，若还有没解决的轨，面板**自己回来**（`rescue_rows_remaining()`） |
| 换好音源后，顶部那条红色"音源没装好"还挂着 | 横幅只在"重新加载工程"时清 | **② 警报必须能自愈**：任何一条让警报前提不再成立的动作（换成同类、装好自动换上、用到当前轨）成功后，宿主**主动**清掉 `engine-error`。⛔ 不能要求用户"再打开一次工程才消失" |
| 横幅里中文提醒与英文按钮叠字 | 消息与按钮抢同一行的空间，谁也不让 | **③ 长的东西必须先缩自己**：消息进 `clip` + `overflow: elide` 的弹性块，动作按钮给固定宽度但内部同样 elide；两者之间留 10px，⛔ 不用 `space-between` 硬顶 |

**"完整测过吗"的回答方式**：这三条不是"看起来好了"，而是有判据
（`crates/yeban-app/tests/missing_sounds_rescue_flow.rs`）：

* 点一次「换成 X」⇒ 读**权威工程**那条轨的 `sampler` 逐字变；同一份工程在同一个渲染入口上
  从"渲染直接失败"变成 `nonzero>0 && peak>0.1` 的另一份输出 —— 证"真的发声"，不是界面说好了；
* 点「下载 X」⇒ 面板让位 + 音源管理在前台 ⇒ 装好那一跳（`rescue_after_pack_installed`）
  **自动**绑上、面板不回来、红字清空 —— 证"不需要第二次点击"。

**顺带抓到的一条真 bug（索引同源）**：救援行的 `track_index` 早先来自
`project.tracks.values().enumerate()`（`BTreeMap` 身份序、且**含主总线**），而界面行下标来自
`display_track_ids()`（主总线不占行）。主总线的身份一旦排在展示轨前面，点「换成 X」就会提交到
**下一条**轨上。规则：**任何"第 N 条轨"都必须与投影同源**（同一个 `display_track_ids()`），
⛔ 不在两处各写一遍枚举。判据用"换完读回权威工程"这一格把它钉住。

### 8.4 为什么这四个问题**没在**本机被发现（自检流程的三处修补）

用户在真机上贴图点破的四件事（面板压住音源管理、下载看不见进度、替换后红字不散、横幅中英文叠字），
本机全部"测过、也看过截图"，却没红 —— 原因不是运气，是**检查的方式**有盲区：

| 盲区 | 具体形态 | 修补 |
| :--- | :--- | :--- |
| **只测"单层"状态** | 既有判据都是"开救援面板"或"开音源管理"，从没构造过**两层同时在场**；层级写反、面板互相遮挡只在同时在场时出现 | 判据必须先构造"用户那一步看到的完整状态"（面板还开着 → 点「下载」），而不是先关一层再开另一层。已落地：`tests/missing_sounds_rescue_flow.rs` 的"下载"腿断言 `panel=false && library=true` |
| **截图只截"舒服尺寸"** | 我截的是 2400×1400；用户窗口更矮。裁切/溢出只在**最小窗口**暴露 | 每轮至少一张 **1200×700**（`min-width`/`min-height`）的整帧；本轮已截「救援面板」「点下载后」两张 |
| **结构性规则只写在脑子里** | `z` 谁大、面板要不要对窗口取上限、去下载要不要先让位 —— 这些"常量关系"没有机械检查，改一行就能回退 | 新增 `tests/ui_layer_contract.rs` 四条守卫：①音源管理 `z` 必须大于救援面板 ②两个面板尺寸必须 `Math.min(…, root.width/height - …)` ③`open_library_for` 必须先收救援面板 ④横幅消息必须 `clip` + `elide` |

**元规则（写进每轮自检清单）**：凡是**用户一眼能看到、而判据看不见**的现象，必须二选一 ——
要么补一条可读的断言，要么写进"每轮手验清单"（截图 + 尺寸 + 看什么），⛔ 不允许只凭"我记得改过"。

#### 8.4.1 顺带查出的待办：救援面板的行内重复 id

为上面第③条做树取证时，`tree_from_element_root` 在"两条轨（2 行 × 3 个候选）"的状态下**直接构造失败**：
`DuplicateId { id: "missing-sounds-candidate" }`。原因写在 `elements.rs` 的注释里 ——
"行内重复 id 是本仓既有的列表口径"。后果：无障碍树 / 控件树导出在这种状态下**起不来**，
音频库列表的多行同理。修法是把 id 带上行/槽下标（本仓已有 `sidebar-item-` + index 的先例），
但注册表是**精确 id** 口径（动态族另有一套 `MODEL_DRIVEN_FAMILIES`），要么给这族登记前缀、
要么把候选按钮改成"行容器唯一、子按钮按 label 寻址"。这条**本轮没动**（改动面跨注册表与判据），
登记为下一轮的 P1。

| P0-4 手势被拒 | 25 处 `eprintln!("…被拒绝（工程未改）")` | 统一 `report_rejected`，文案带"再试一次 / 否则说明这一步当前不适用" |
