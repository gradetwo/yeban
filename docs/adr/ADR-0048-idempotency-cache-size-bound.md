# ADR-0048 — 幂等缓存的**条目数**没有上界：超限时"拒绝／驱逐／降级"三条路都要动契约保证，属产品裁决

- **状态**: **Proposed**（待人类批准；⛔ 集成者代签 —— 本票不改任何代码，只把实测边界与三条可选路线登记成可批可驳的裁决）
- **决定者**: 待人类裁决（集成者提出）
- **关联**: `ADR-0001`（D25：`ToolResponse.error.code` 是**闭合**的 20 值联集）、
  `ADR-0047`／`ADR-0042`（同类"Proposed 待批"的写法先例）、`MCP-TOOL-001`、
  `ARCH-SEC-002`（控制面安全）、R142（"静默永不生效"）、本会话的**幂等键作用域**修复（`0861966d`）
- **实现落点**: ⛔ 本票无落点。若批 `D2`／`D4`，落点在 `crates/yeban-mcp/src/dispatch.rs`
  的 `evaluate_tool_call` 第 6/7 步之间，且**都要改契约**（错误码或响应字段）。

## 背景（先测后改，AGENTS.md §6）

**这个数字在数什么**：`Dispatcher` 的幂等缓存**能容纳多少条**（单位＝条），以及**有没有**
任何淘汰/拒绝逻辑（单位＝处）。

现读（2026-10-29，`grep -rn "evict\|capacity\|CAP\|IDEMPOTENCY" crates/yeban-mcp/src/dispatch.rs`
⇒ **0 处**）：

1. 缓存字段 `dispatch.rs:141`：`idempotency: BTreeMap<String, CachedOutcome>` —— 无容量参数。
2. 写入点 `dispatch.rs:389-396`：**只要**调用带非空 `idempotencyKey` 就 `insert`，⛔ 任何上限判断。
3. 读取点 `dispatch.rs:376-382`：命中即返回；⛔ 刷新顺序（不是 LRU，`BTreeMap` 按字典序）。
4. **键长**有上界：`tools.rs:436-439` 的 `max_len: Some(256)`（schema `maxLength: 256`，D46 收口）；
   schema 里的理由原文是"无界键会成为无界的内存驻留缓存, 属资源耗尽面" ⇒ **只堵了键长，没堵条目数**。
5. 缓存**跨工程生命周期**：它挂在 `Dispatcher`（`dispatch.rs:137-145`），⛔ 在 `Domain` 里；
   `yeban_open_project`／`yeban_close_project` 都**不**清它（`grep "idempotency.clear|idempotency.remove"` ⇒ 0 处）。
   且**一个进程只有一个 `Dispatcher`**：形态 B 在 `bin/yeban-mcp.rs:210` 建一次并交给
   `serve_http`／`serve_stdio`，HTTP 侧长期持有 `Mutex<Dispatcher>`（`transport/http.rs:545`）
   ⇒ 条目数在一个**长驻进程**里随**不同键**的调用次数线性增长，每条持一整份首次响应载荷
   （`query_project` 的稀疏视图、渲染摘要这类载荷可达数十 KB 量级）。

⇒ 这是**真实的资源面**，但**不是可以自行选一个策略就改**的东西：三种"设上限"的做法都会碰到
本项目最核心的保证或闭合契约。这正是本票要人类择一的原因。

## 为什么不能自行发明（三条硬约束，全部现读）

1. **静默淘汰会破坏"同键不重复施加副作用"**：被逐出的键再请求 ⇒ 第 6 步不命中 ⇒ 第 7 步**重新执行**
   ⇒ 正是本会话 `0861966d` 修的同一类缺陷（副作用发生而调用方以为只是重放），只是触发条件从
   "跨工具撞键"换成"缓存满了"。⇒ `D3`（淘汰最旧）**直接与保证冲突**，除非响应里明确标注。
2. **"超额拒绝"的码有先例，但用法要确认**：`ToolResponse.error.code` 是**闭合**联集
   （`ADR-0001` D25，20 值，`tools.rs:174-219` 现读）。**场景启动队列满**已经用
   `ErrorCode::Busy` + `data.reason: "sceneLaunchQueueFull"` 响亮拒绝（`mod.rs:3804-3812`），
   且那条有界队列的注释写明理由 —— "否则控制面变成一条内存泄漏"
   （`scene_launch.rs:43-45`，`MAX_PENDING_SCENE_LAUNCHES = 64`，与引擎事件环 `EVENT_CAPACITY = 256`
   同量级）。⇒ 同理可写 `BUSY` + `reason:"idempotencyCacheFull"`，**不需要新错误码**；
   但这会把 `BUSY` 的"引擎正忙"语义再扩一次（`tools.rs:202` 的注释），**要不要扩、上限取多少**，
   仍是产品裁决。⚠ 初版本票写成"没有语义匹配的码"，是被 `BUSY` 的**注释**误导 ——
   先例在**消费点**而不在枚举注释里（AGENTS.md §6 第 3 条）。
3. **"降级为尽力而为"需要一个响应字段**：若超限时"照常执行但不缓存"，调用方必须**看得见**
   （否则它以为重试是安全的）⇒ 要么加 `replayed:false`＋`idempotency:'notRecorded'` 之类的新字段
   （改 `ToolResponse` 形状），要么接受**静默降级**（与 R142 的教训对冲）。

## 四条路线（人类择一：D1 不做／D2 拒绝／D3 驱逐／D4 降级）

### D1 —— 明确不设条目上限（零代码，只文档化）

- 做法：在 `mcp-core-notes` 的 M7 段写明"缓存无条目上限；生命周期＝`Dispatcher` 会话
  （关工程不清）"；schema 的 `idempotencyKey` 描述同步。
- 理由：控制面**只绑 `127.0.0.1` + Bearer token**（红线 5），增长由**已授权**调用方驱动；
  真要 DoS 有更直接的手段（大载荷工具）。键长已有界，"每条 ≤256 字节元数据 + 一份载荷"是可解释的。
- 代价：长驻会话的内存**只增不减**；与场景启动队列"必须有界"的既有立场**不一致**。
- 可测性：无需新判据；可补一条**文档一致性**判据（描述里出现"无上限"字样）—— 但那是针，⛔ 证行为。

### D2 —— 条目数上限 + **响亮拒绝**（推荐；有先例，零新错误码）

- 做法：`const MAX_IDEMPOTENCY_ENTRIES: usize`（建议 4,096，理由＝一条 10 KB 载荷 × 4096 ≈ 40 MB 量级，
  ⛔ 拍脑袋值，请人类定）；第 6 步之前：`len() == MAX && !contains(key)` ⇒ 返回
  `BUSY` + `data.reason:"idempotencyCacheFull"`（附 `entries`/`max`），**不执行**。
- 语义：拒绝是**安全的**（副作用不发生），但客户端必须**换一个会话**才能继续用幂等 ——
  因为没有"清缓存"工具（工具面 25 个里没有；加一个都是新票）。
- 需要裁决：`BUSY` 语义扩展是否可接受 + 上限值。
- 可测性：`idempotency_cache_rejects_new_key_at_capacity`（用**测试专用**的小上限注入，
  ⛔ 真跑 4,096 次）＋"拒绝时副作用不发生"判据。

### D3 —— 上限 + 淘汰最旧（⛔ 与核心保证冲突，仅登记）

- 做法：超限时逐出字典序最小/最旧的键，正常执行并缓存新键。
- 代价：被逐出的键**再请求会重新执行** ⇒ 与"同 key 不重复施加"直接冲突（见上 §1）。
  若仍要做，必须让"缓存缺失"**可区分于"首次执行"**（例如响应加 `cacheState` 字段），
  那就已经不是"淘汰"而是 D2/D4 的变体。
- 可测性：判据会**钉死一个缺陷语义**（重放 ⇒ 二次副作用），⛔ 推荐。

### D4 —— 上限 + **不缓存但仍执行**（降级，需新响应字段）

- 做法：超限时照常执行，但**不写缓存**，响应注明"本次未记录幂等"。
- 语义：客户端看到字段就知道"重试有风险"；⛔ 拒绝，所以不会卡死会话。
- 需要裁决：新字段名与形状（`ToolResponse` 顶层？`data` 里？）—— 都要改 schema 与既有样本。
- 可测性：`idempotency_cache_degrades_loudly_at_capacity`（字段出现 + 第二次调用**真执行**）。

## 本票的边界

- ⛔ 本票不改代码、不改 schema、不改任何错误码；`dispatch.rs:141` 保持 `BTreeMap` 无上限。
- 推荐 `D2` 的理由：**场景启动队列已经确立了"控制面容器必须有界 + 响亮拒绝"的立场**
  （`scene_launch.rs:43-45` 的注释原话是"否则控制面变成一条内存泄漏"），幂等缓存放任增长
  与那条立场**不一致**；而 `D2` 有现成的码与形状先例，⛔ 破契约。
  ⚠ 但"D1 补文档"这件事**不需要裁决**（只是描述现状），已单独写入 `mcp-core-notes` M7。
