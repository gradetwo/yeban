# ADR-0003 — 顶栏保存按钮的槽位（挪徽章 vs 改规范序列）

- **状态**: **Proposed（待人类裁决）**
- **决定者**: 集成者（Agent）在负责人授权范围内提出；最终口径归负责人
- **关联**: `ROAD-M4-008`（用户够得到的保存入口）；`UI-MCP-003` / `MUST-GATE-015`（分平台 Golden 与视觉回归）；
  `UI-GRID-001`（UI/UX 规范 §1.1 的顶栏序列）；自 `d180bfb` 起持续变红的 CI run；
  基准目录 `crates/yeban-app/tests/golden/linux/`（含其 `MANIFEST.txt`）
- **日期**: 2026-10-06

## 背景（规范没有为这个元素定义槽位）

四份 Normative 规范给了顶栏的**序列**，却**没有**给 `ROAD-M4-008` 要求的"用户够得到的保存入口"任何槽位。
这条空隙在 `d180bfb` 落地保存按钮的那一刻变成了红灯，今天必须做个选择才能让 CI 重新有判决力。

### (a) 基准是**过期**的，不是 flake

Linux Golden（5 张 PNG，`crates/yeban-app/tests/golden/linux/`）由手动档 `gates-manual.yml` 的 `goldens` 档生成，
其 `MANIFEST.txt` 记录 run id **`37341930317`**、生成时间(UTC) **`2026-10-05T16:36:00Z`**。
保存按钮由 **`d180bfb`**（提交时间 `2026-10-06T20:06:19+08:00` = `2026-10-06T12:06Z`）引入
⇒ 基准比它**早约 20 小时**。因此从 `d180bfb` 起的红是**确定性的基准过期**，重跑不会绿。

### (b) 像素差是确定的、局部的（两次独立测量）

两条独立工作线下载了失败 run 的 artifact，得到同一结论：四次红 run 产出的 PNG **两两逐字节相同**；
与已提交基准的差是 **268 个像素单元（cell）**，全部落在包围盒 **`x 580..591 × y 8..39`**（12 px 宽 × 32 px 高），
其中 **242 个 cell 是把 `#151d38` 变成 `#1b2447`**
（`Tokens.bg-panel` → `Tokens.bg-panel-alt`，即新元素自己声明的填充色），另 **26 个 cell 是抗锯齿的圆角混合**。
2,073,600 个 cell 中有 **2,073,332 个逐字节相同** ⇒ 顺序、计时器、字体、判据互相干扰都被排除。

### (c) 碰撞：按钮被规范元素遮住

`transport-save-button` 占 `x 580..636`（56 × 32 px）；规范元素 `transport-ai-proposal-badge` 占 `x 588..708`
（120 × 32 px），在 `crates/yeban-app/ui/transport.slint` 里**声明在后** ⇒ 后画的盖在上面。于是：

- **56 px 中有 48 px 被遮挡（85.7%）**；
- 标签「保存」（居中于 `x 594..622`）**100% 被遮挡**。

即这个按钮在规范语义上**既不完整可见、也无法被读出**，而它正是 `ROAD-M4-008` 选项 (a) 要的那个入口。

### (d) 簇里没有它的位置

从 `crates/yeban-app/ui/transport.slint` 读出的几何（并与已提交基准的像素独立复核一致）：
分支 `372..500`、Commit `508..540`、回滚 `544..576`、AI 徽章 `588..708`；
簇内自由间隙只有 **8 px（分支→Commit）、4 px（Commit→回滚）、12 px（回滚→徽章）**。
**没有任何簇内位置装得下 56 px 的按钮**（最大的自由间隙只有 12 px）。

右侧视图切换组锚在 `root.width - 304px`，1920 px 宽时起点为 **1616 px**；
组内间隙 **4 / 8 / 8 px**、尾部 **24 px**。

### (e) 规范序列里没有保存槽位

UI/UX 规范 §1.1（约第 67 行）给出的规范顶栏序列是
`走带 / BPM / [Branch: main ▼] / [Commit ↺ ↻] / [🟣 AI提案 (1)] / 视图切换` —— **没有保存槽位**。
这正是"规范对某个实现细节**没有**定义"的情形，因此按 `docs/adr/README.md` 的规则，
裁决写在这里、明确标注 `Proposed`，**不改 Normative 正文**。

### (f) 判据只比**原始编码字节**，本机绿没有意义

`crates/yeban-app/src/test_port_adapter.rs::assert_matches_golden` 把新渲染的帧经 `png::encode_rgb8`
编码后与 `tests/golden/<platform>/<name>.png` **逐字节**比对；平台目录不存在时它只打印一行
「…⇒ 视觉回归**未被判定**（不等于通过）」并 `return`（**不**断言）。
本仓库只有 `tests/golden/linux/`，**没有** `tests/golden/macos/`
⇒ 本机 macOS 上跑这条判据**什么都不判**，本机绿不是证据。

## 决定（Proposed）

**A（最小改动）：改规范序列，按钮不动，挪徽章。**

1. 把 UI/UX 规范 §1.1 的规范顶栏序列改为
   `走带 / BPM / [Branch: main ▼] / [Commit ↺ ↻] / [保存] / [🟣 AI提案 (1)] / 视图切换`；
2. `transport-save-button` **保持 56 × 32 px、`x: 580px`** —— 它在回滚（`544..576`）之后 4 px，
   与簇内既有的 4 px 节奏一致；
3. `transport-ai-proposal-badge` 从 `x: 588px` 移到 **`x: 640px`**（右移 **52 px**，
   与按钮之间留 **4 px** 间距，尺寸 120 × 32 px **不变**）。其新右边缘为 **760**，
   到右锚视图组的 **1616** 之间余 **856 px** ⇒ **其它元素一个都不动**。

**批准后唯一的代码 diff** 是 `crates/yeban-app/ui/transport.slint` 里徽章那一行 `x:`。
`elements.rs`（`transport-save-button` 在 `:228`、`transport-ai-proposal-badge` 在 `:270`，
两者只登记 ID 与无障碍标签，与坐标无关）、`app.slint`（`save-project` 回调与 `save-status` 的接线）、
`host::wire_save`（`host.rs:470`）、`save_action::dispatch_save`（`save_action.rs:151`）
与 `save-status` 的写入侧（`host::apply_save_outcome`）**都不需要改**。

## 代价（必写）

1. **5 张 Linux 基准要再生成一次**（一次性）：按钮与徽章都进入画面 ⇒ 5 张 PNG 全部变化。
   再生成只能按下面"批准后的再生成程序"那节走，**不得手改任何 sha256**。
2. **规范 §1.1 的正文要由人类改一次**：序列里插进 `[保存]`。Agent 不代改 Normative 正文（ADR 目录规则）。
3. **顶栏左半段的密度上升、节奏不再均匀**：原本是"8 / 4 / 12 px"三段间隙，
   改后是"8 / 4 / 4 / 4 px"（分支→Commit→回滚→保存→徽章）——
   把一个规范未定义的元素收编进序列，代价就是左半边不再是单一节奏。
4. **顶栏中段更空**：徽章右移到 760 后，`760..1616` 成为一段连续空白（856 px）。

## 备选方案及其代价（逐条否决的理由）

1. **把按钮缩进 12 px 的自由间隙**（回滚与徽章之间）：即使缩成 32 × 32 px 的纯图标也**放不下**
   （12 < 32）；而把标签「保存」留在外面会**横跨回滚与徽章**两个元素。**否决**。
2. **放在徽章右边 `x 716..772`**：不与任何元素碰撞，但它在规范序列里
   **插入了一个规范没有定义的顶栏槽位**（徽章与视图切换之间），等于让规范正文与实现继续不一致。**否决**。
3. **放在 `708..1616` 的 908 px 空洞里**：同样是一个**悬空的新槽位**，
   且离文档级动作（分支 / 提交 / 回滚）很远，语义割裂。**否决**。
4. **放进右侧视图切换组**：组内间隙只有 4 / 8 / 8 px、尾部 24 px，装 56 px 会**碰撞**；
   把整组左移又会改动 4 个已规范化的元素位置。**否决**。
5. **把按钮移到状态栏，紧挨既有的 `status-bar-save-status`**（`crates/yeban-app/ui/status_bar.slint:96`）：
   顶栏因此保持规范原样，但**把主操作降级**到 24 px 高的状态栏（状态栏还可能有自己的规范），
   而保存是**文档级动作**，与走带 / 提交同一族。**否决**。
6. **只留键盘快捷键，不要按钮**：不需要改规范，但会**削弱 `ROAD-M4-008` 选项 (a) 要求的
   "用户够得到的入口"**（纯键盘不构成"够得到"的按钮入口），而且快捷键本身**仍需要在规范里有一行**。**否决**。

## 批准后的再生成程序（引用已批准的机制，不发明新流程）

批准（且代码 diff 落地）之后，基准**只能**按仓库既有的手动档再生成：

1. `gh workflow run gates-manual.yml -f gate=goldens` —— 该档跑
   `YEBAN_WRITE_GOLDEN=1 cargo test -p yeban-app --locked --test real_ui_tier1`，
   于是 5 张 PNG **全部被写出**（`regenerate_golden_if_asked`）；
2. 下载该 run 的 **`golden-linux`** artifact；
3. 用 artifact 里的 5 个文件**替换** `crates/yeban-app/tests/golden/linux/` 下的同名文件；
4. 重写 `tests/golden/linux/MANIFEST.txt`：新的 **run id**、新的**生成时间戳**、
   以及**每个文件的新 sha256**。

清单自己的正文把这次**入库**指派给**集成者在复核之后**执行。
在拿到那次 run 之前，**任何 run id 与 sha256 都不得被写出来** ——
清单现在仍带 **pre-`d180bfb`** 的旧哈希，并已明确标注，这是正确的状态。

## 这条修复将如何被判定（套用仓库自己的新规则）

判"修复绿"必须按 `AGENTS.md` §6.3 的三条防伪规则来读：

1. **读该提交自己的 run**：`gh run list` 里 `headSha` 必须是那个提交（tip 绿只覆盖 tip）；
2. **计划器必须真的选中 `yeban-app`**：该 push run 的 planner 必须返回 `workspace_wide: true`，
   **或** `crates` 列表里含 `yeban-app`。纯文档改动会返回 `{"crates": [], "workspace_wide": false}`，
   于是所有 Rust 作业显示 `-`、耗时 `0s`、整体却是 success —— 那是**空绿**；
3. **目标作业必须真的执行过**：测试步骤耗时**非零**，且日志里有 `test result:` 行。
   **跳过的作业不是绿，不构成证据。**

另外：**编码后的字节数 6,222,418 字节不能证明任何内容**。本仓的 PNG 写入器是**存储式 deflate**，
长度 = `raw + ceil(raw/65535)×5 + 63`，1920 × 1080 恒为 **6,222,418 字节**
⇒ "基准 N 字节 / 当前 N 字节"这种比较**不含信息**；要判内容必须比**哈希**或**逐像素**
（并给出差异包围盒与前几个差异像素的颜色）。
