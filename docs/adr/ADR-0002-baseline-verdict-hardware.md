# ADR-0002 — BASELINE 系列的判定硬件（参考机 vs 托管 runner）

- **状态**: **Proposed（待人类裁决 HD-49）**
- **决定者**: 集成者（Agent）在负责人授权范围内提出；最终口径归负责人
- **关联**: 待人类裁决 **HD-49**；门禁行 `docs/ledger/gate-status.md` 的 `BASELINE-003`
- **日期**: 2026-10-05

## 背景（规范之间的空隙，而非冲突）

四份 Normative 规范给出了**门限**（帧率 120 FPS / p99 ≤ 8.3 ms、时延往返 ≤5.5 ms、峰值常驻内存 ≤35 MB 等），
但**没有**规定"用哪台机器、什么频率来判定"。这条空隙今天必须做个选择，否则 BASELINE 系列只能一直悬着：

- `spikes/README.md:36` 与 **HD-45**：帧率判决**保留给参考机**（负责人指定 MacBook Pro M2 Max）；
- `.github/workflows/gates-manual.yml` 的 `pending`/`inventory` 档**自述**：BASELINE 系列需要**固定频率的参考硬件**，
  而 GitHub 托管 runner **频率不固定**；
- 因此这不止关乎 `BASELINE-003`：`BASELINE-001`（离线渲染吞吐）、`BASELINE-002`（峰值内存）等同样受影响。

## 决定（Proposed）

**A：BASELINE 系列只在参考机上判定。** 托管 runner 的读数一律作为**量级证据**记录，**不得**作为门禁判决。

在负责人裁决之前，集成者的处置是**维持 PENDING 且不自行放宽规则**（第 198 轮），而不是"先按托管读数判了再说"。

## 代价（必写）

1. **BASELINE 系列在参考机 runner 就位前一律 PENDING** —— 也就是"完成度"上少几项可宣称的达标；
2. 参考机 runner 需要**硬件/预算**（`HD-38` 曾记为无预算），非 Agent 可决；
3. `ROAD-M3-002` 的**批量绘制（步骤 ④）**在口径定案前**无法验收**（第 205 轮）：改渲染器会改掉被测量的东西。

## 备选方案 B 及其代价

**B：接受托管读数并写明局限。** 代价是**判定随硬件漂移**，且本会话**实测**了这种不稳定性：同一口径两次跑得
`6.477/9.831 ms` 与 `8.450/8.802 ms` —— **两者之差大于到 8.3 ms 门限的距离**，即同一提交可以"过"也可以"不过"。
⇒ 采用 B 会让门禁判决**不可复跑地稳定**（违反 L31 的精神）。这是**反对** B 的**测量**依据，而不只是偏好。

## 可推翻性

本裁决**可被推翻**：负责人若裁 B，本文件**更新**（不另开一份），并把"接受托管读数"的局限写进每一条 BASELINE 行；
若裁 C（维持 PENDING），本文件的决定项照旧、状态改为 Accepted（口径=待参考机）。
