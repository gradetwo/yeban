# ADR-0002 — BASELINE 系列的判定硬件（参考机 vs 托管 runner）

- **状态**: **部分 Accepted / 部分 Proposed** —— `## 裁决（2026-10-07，负责人批准）` 一节（`BASELINE-003` 的**正式口径 = 绘制回调耗时 ≤2ms**）已获负责人批准；`## 决定（Proposed）` 那一节的**硬件**口径（参考机 vs 托管 runner 的适用范围）仍 **Proposed（待 HD-58/HD-49）**
- **决定者**: 集成者（Agent）在负责人授权范围内提出；最终口径归负责人
- **关联**: 待人类裁决 **HD-49** / **HD-58**；已裁决 **HD-59**（本次口径裁决）；门禁行 `docs/ledger/gate-status.md` 的 `BASELINE-003`
- **日期**: 2026-10-05（本文）；2026-10-07（`## 裁决` 一节）

## 背景（规范之间的空隙，而非冲突）

四份 Normative 规范给出了**门限**（帧率 120 FPS / p99 ≤ 8.3 ms、时延往返 ≤5.5 ms、峰值常驻内存 ≤35 MB 等），
但**没有**规定"用哪台机器、什么频率来判定"。这条空隙今天必须做个选择，否则 BASELINE 系列只能一直悬着：

- `spikes/README.md:36` 与 **HD-45**：帧率判决**保留给参考机**（负责人指定 MacBook Pro M2 Max）；
- `.github/workflows/gates-manual.yml` 的 `pending`/`inventory` 档**自述**：BASELINE 系列需要**固定频率的参考硬件**，
  而 GitHub 托管 runner **频率不固定**；
- 因此这不止关乎 `BASELINE-003`：`BASELINE-001`（离线渲染吞吐）、`BASELINE-002`（峰值内存）等同样受影响。

## 决定（Proposed）

**A：BASELINE 系列只在参考机上判定。** 托管 runner 的读数一律作为**量级证据**记录，**不得**作为门禁判决。

在负责人裁决之前，集成者的处置是**维持 PENDING 且不自行放宽规则**（第 198 轮），而不是"先按托管读数判了再说"。

## 代价（必写）

1. **BASELINE 系列在参考机 runner 就位前一律 PENDING** —— 也就是"完成度"上少几项可宣称的达标；
2. 参考机 runner 需要**硬件/预算**（`HD-38` 曾记为无预算），非 Agent 可决；
3. `ROAD-M3-002` 的**批量绘制（步骤 ④）**在口径定案前**无法验收**（第 205 轮）：改渲染器会改掉被测量的东西。

## 备选方案 B 及其代价

**B：接受托管读数并写明局限。** 代价是**判定随硬件漂移**，且本会话**实测**了这种不稳定性：同一口径两次跑得
`6.477/9.831 ms` 与 `8.450/8.802 ms` —— **两者之差大于到 8.3 ms 门限的距离**，即同一提交可以"过"也可以"不过"。
⇒ 采用 B 会让门禁判决**不可复跑地稳定**（违反 L31 的精神）。这是**反对** B 的**测量**依据，而不只是偏好。

## 裁决（2026-10-07，负责人批准）：`BASELINE-003` 的正式口径 = **绘制回调耗时（不含呈现）**

**入口**：`HD-59`（`docs/ledger/human-decisions.md`）。**这不是**"待人类裁决"—— 负责人已就该口径明确指示，故本节的`状态`是 **Accepted**（本文件关于**硬件范围**的那一节仍 Proposed）。

### 背景（由测量建立，不是偏好）

上一片第一次把 `BASELINE-003` 的仪器搬到**规范假设的 GPU 路径**（`winit` + FemtoVG/OpenGL）上，并在参考机取到正式读数：

- **墙钟帧间隔**：p99 = **9.837 ms**（7 次 9.837–10.380），p50 8.328 ms，599 帧里 **358 帧 > 8.3 ms**；
- **对照实验**（同场景、同计时器，**只换渲染器**）：`femtovg` p99 **10.389 ms** / `software` p99 **10.123 ms** ⇒ 两条路径落在**同一个 ~10 ms 周期**上；同一次运行的 CPU 只有 **6.5 s 墙钟里的 0.24 s user**；
- 本机面板是**自适应刷新率**（`ioreg` 报 `APTLimitRefreshRate = No`；刷新区间 5:1、同一分辨率 6 档），规范"固定刷新率"的**前提在本参考机上不成立**。

⇒ 那 10 ms 周期是**面板的呈现节奏**，**不是**产品的绘制成本；**即使零成本渲染器也不可能**在本机上满足"墙钟 p99 ≤ 8.3 ms"。

### 决定（Accepted）

1. **正式门禁口径 = 绘制回调耗时（不含呈现）**：由 `slint::Window::set_rendering_notifier` 的
   `RenderingState::BeforeRendering` → `RenderingState::AfterRendering` 区间给出；
   **门限取规范自己的数** —— `[UI-NOTE-001]` 步骤 ④ 的 **≤ 2 ms**
   （`docs/YEBAN_DESKTOP_UI_UX_AND_INTERACTION_REDESIGN.md:172-174`）。
2. **墙钟帧周期降级为环境读数**：照采、照打，但**明确标注为非门限**（它记的是参考机的面板行为）。
3. ⛔ **这不是放松**：产品面向的预算仍是规范那个数（**2 ms 比 8.3 ms 更紧**）；
   改变的只是"不再拿面板的节奏评判产品"。

### 为什么这个区间就是"绘制成本（不含呈现）"（上游语义，逐字）

- `AfterRendering` 的官方文档原文："the scene of items was rendered, but the back buffer was
  **not** sent for display presentation yet (for example GL swap buffers)"
  （`i-slint-core-1.18.1/api.rs:346-348`）；
- FemtoVG 在 `AfterRendering` **之后**才调用 `present_surface()`
  （`i-slint-renderer-femtovg-1.18.1/lib.rs:332-335`），而该后端的 `submit_commands` 是**空实现**
  （`i-slint-renderer-femtovg-1.18.1/opengl.rs:265`），真正送显的 `swap_buffers()` 在
  `present_surface()` 里（同文件 `:275`）。

⇒ 采样区间覆盖"录绘制命令 + 转命令缓冲"，**不含**缓冲交换/垂直同步。

### 能测到哪一步，测不到哪一步（如实）

Slint **不把**"钢琴卷帘那批矩形的绘制"单独交给用户代码：本仓卷帘是 `.slint` 声明式组件
（`crates/yeban-app/ui/console/piano_roll.slint` 的 `for note_ulid[...]`），因此**没有**用户级
绘制回调可计时；`set_rendering_notifier` 给的是**整窗场景**的绘制回调 —— 它是规格对象的
**超集**（传输条 / 混音台 / 编曲 / 卷帘 + femtovg 命令缓冲转换 + 纹理缓存排空）。
⇒ 读数的方向性：整窗都超 2 ms 时**不能**据此断言卷帘那一批矩形超 2 ms；反之若整窗 ≤ 2 ms，
则卷帘那批必然 ≤ 2 ms。这是"最接近的诚实测量"，不是规格对象的等价物。

### 代价（必写）

1. 正式读数仍与**参考机**绑定（托管 runner 无 GPU ⇒ 软件光栅化，按其自身理由仍不可作判决）；
2. 量的是**整窗**绘制回调，不是卷帘批绘制本身（见上）；
3. **新实测读数（本机，2026-10-07，6 次）**：绘制回调 p99 = **2.440 / 2.441 / 2.504 / 2.551 / 2.956 / 3.049 ms**
   （p50 2.056–2.788 ms；573–598 / 598–599 次回调 > 2 ms）⇒ **正式口径下本门禁未达标**，
   `BASELINE-003` 保持 **PENDING**，理由从"有意挂起/缺硬件"变为"**已量到读数、读数未达标**"。
   按本仓纪律**不调参以求通过**（逐次读数与命令见 `docs/ledger/gate-status.md` 的 `BASELINE-003` 行）。

## 可推翻性

本裁决**可被推翻**：负责人若裁 B，本文件**更新**（不另开一份），并把"接受托管读数"的局限写进每一条 BASELINE 行；
若裁 C（维持 PENDING），本文件的决定项照旧、状态改为 Accepted（口径=待参考机）。

**2026-10-07 的口径裁决同样可被推翻**：若负责人改判"以墙钟帧周期为门限"，则必须**同时**给出满足规范
"固定刷新率"前提的硬件；届时本文件**更新**本节并把 `HD-59` 标注为已改判（不删原记录）。
